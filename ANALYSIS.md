# Instrumentarium — Глубокий анализ проекта
## Дата: 2026-06-09

---

## 1. АРХИТЕКТУРНЫЕ ПРОБЛЕМЫ

### 1.1. Двойная структура кода (КРИТИЧНО)
**Проблема:** Существуют ОДНОВРЕМЕННО два серверных кода:
- `/server.py` — монолит (~765 строк) с тестами для него
- `/server/` — подпакет с `__init__.py`, `state.py`, `utils.py`, `errors.py`, `setup.py`

**Проблемы:**
- Тесты с `@patch("server.xxx")` патчат подпакет, но `server.py` (монолит) имеет свою копию функций → тесты не покрывают реально работающий код
- `app.py` импортирует `from server import ...` (подпакет), но если запустить `server.py` напрямую — работает другая версия
- CI собирает `server.py` в PyInstaller, а не `server/` подпакет
- Путаница: какой файл является точкой входа?

**Рефакторинг:** Удалить `/server.py` полностью. Весь код перенести в `/server/` подпакет. Точка входа: `python -m server`.

### 1.2. Глобальное состояние через синглтон
**Проблема:** `state = AppState()` в `server/state.py` — модульный синглтон.

**Риски:**
- Потокобезопасность: `setup_messages` — список, к ноторому обращаются из разных потоков без блокировки (lock защищает только `cookies_path` и `active_proc`)
- Тестирование: синглтон сохраняет состояние между тестами → тесты не изолированы друг от друга
- `download_jobs` и `probe_meta_jobs` — глобальные словари без очистки (утечка памяти при длительной работе)

**Рефакторинг:** Использовать dependency injection или контекстный объект, передаваемый в обработчики.

### 1.3. HTTP-сервер в одном потоке
**Проблема:** `http.server.HTTPServer` — однопоточный блокирующий сервер.

**Последствия:**
- `/probe` блокирует сервер на 30 секунд при медленном интернете
- `/download` (через `_wait_deps`) блокирует на 30 секунд
- Одновременно можно обработать только один запрос

**Рефакторинг:** Использовать `ThreadingHTTPServer` или `ThreadPoolExecutor`.

## 2. БАГИ И ПРОБЛЕМЫ КОДА

### 2.1. [КРИТИЧНО] download_jobs и probe_meta_jobs — утечка памяти
**Где:** `server.py:123-124`
**Проблема:** Словари никогда не очищаются. Каждое скачивание/проба добавляет запись. При длительной работе память растёт неограниченно.
**Исправление:** TTL-очистка, максимум N последних записей, или `weakref.WeakValueDictionary`.

### 2.2. [КРИТИЧНО] JobLogger.run() — незащищённый доступ к download_jobs
**Где:** `server.py:201-331`
**Проблема:** `j = download_jobs[self.job_id]` — доступ без блокировки. Если два JobLogger запущены одновременно (баг или race condition), возможна гонка данных.
**Исправление:** Использовать `threading.Lock` или `collections.defaultdict` с атомарными операциями.

### 2.3. [КРИТИЧНО] _handle_download не проверяет deps_ready корректно
**Где:** `server.py:690-719`
**Проблема:** Если `setup_phase == "silent_check"`, вызывается `_wait_deps()` который отправляет JSON-ответ и делает `return`. Но если deps не готовы за 30 секунд — timeout, и клиент никогда не получит ответ.
**Исправление:** Возвращать deps_ready=false клиенту и позволить ему повторить запрос.

### 2.4. [СРЕДНЕ] Probe timeout не настраивается
**Где:** `server.py:527` — `timeout=30` захардкожен
**Проблема:** Для медленных соединений или тяжёлых сайтов 30 секунд может не хватить. Для быстрых — слишком долго ждать.
**Исправление:** Вынести в конфигурацию/PyInstaller env.

### 2.5. [СРЕДНЕ] setup_messages не потокобезопасен
**Где:** `server/state.py:91-98`
**Проблема:** `setup_messages` — обычный список. `add_message` вызывается из setup thread, а `get_setup_response` — из HTTP thread. Нет lock.
**Исправление:** Использовать `deque` с maxlen + lock, или `queue.SimpleQueue`.

### 2.6. [СРЕДНЕ] probe_meta_jobs поллируется клиентом без бэк-оффа
**Где:** `download.html:583-613`
**Пролем:** Каждые 1.5 секунды × 12 попыток = 18 секунд поллинга. Сервер получает 12 HTTP-запросов для одной пробы.
**Исправнение:** Экспоненциальный бэк-офф: 1s, 2s, 4s, 8s...

### 2.7. [СРЕДНЕ] JS: currentDuration не объявлена через let/const
**Где:** `download.html:557` — `currentDuration = data.duration || 0`
**Проблема:** Переменная создаётся глобально (без `let`/`const`/`var`). В strict mode вызовет ошибку.
**Исправление:** `let currentDuration = ...` в начале скрипта.

### 2.8. [СРЕДНЕ] JS: doProbe использует fetch, но probe-meta — XMLHttpRequest
**Где:** `download.html:545` (fetch) vs `download.html:695` (XHR)
**Проблема:** Непоследовательность. pywebview на некоторых платформах не поддерживает fetch к localhost (из-за CORS/cookie policy).
**Исправление:** Привести всё к XMLHttpRequest.

### 2.9. [НИЗКОЕ] _probe таймаут убивает yt-dlp, но не возвращает partial data
**Где:** `server.py:527-531`
**Проблема:** Если yt-dlp завис на 29 секунд из 30, и таймаут срабатывает — все данные теряются.
**Исправление:** Уменьшить timeout до 15s + кэширование результата.

### 2.10. [НИЗКОЕ] Нет CORS-заголовков в HTTP-ответах
**Где:** `Handler._json()` — не добавляет `Access-Control-Allow-Origin`
**Проблема:** Если UI открыт из файловой системы (file://) или другого origin, fetch/xhr запросы заблокируются.
**Исправление:** Добавить CORS-заголовки для всех JSON-ответов.

## 3. ПРОБЛЕМЫ БЕЗОПАСНОСТИ

### 3.1. [КРИТИЧНО] Path traversal в _serve_html_file
**Где:** `server.py:348-367`
**Проблема:** Если `self.path` содержит `../../etc/passwd`, сервер попытается прочитать этот файл (хотя и ищет только `download.html`).
**Исправление:** Валидировать path, использовать `os.path.realpath()` и проверять что файл внутри SCRIPT_DIR.

### 3.2. [СРЕДНЕ] Cookies файл сохраняется без валидации
**Где:** `server.py:669-688`
**Проблема:** Content из запроса декодируется из base64 и записывается в `.cookies.txt` без валидации. Можно записать произвольный файл.
**Исправление:** Валидировать формат cookies (Netscape), ограничить размер.

### 3.3. [СРЕДНЕ] Нет rate-limiting на /probe и /download
**Проблема:** Злоумышленник (или баг в UI) может отправить сотни запросов → сотни yt-dlp процессов.
**Исправление:** Rate limiter (например, token bucket).

### 3.4. [НИЗКОЕ] URL из запроса напрямую передаётся в subprocess
**Где:** `server.py:521` — `cmd.append(url)`
**Проблема:** Хотя yt-dlp сам экранирует аргументы, отсутствие валидации URL потенциально опасно.
**Исправление:** Проверять URL перед передачей.

## 4. ПРОБЛЕМЫ ТЕСТИРОВАНИЯ

### 4.1. [КРИТИЧНО] Тесты не покрывают HTTP-обработчики
**Проблема:** Все 23 теста — unit-тесты для utility-функций. Нет интеграционных тестов для `/probe`, `/download`, `/status`, `/shutdown`.
**Исправление:** Добавить `pytest` + `http.client` тесты, запускающие сервер в thread.

### 4.2. [СРЕДНЕ] Тесты не очищают синглтон state между запусками
**Проблема:** `from server import state` — импортирует тот же синглтон. Если `test_app_state_reset_setup` выполняется после `test_status_endpoint_json`, state уже загрязнён.
**Исправление:** Добавить fixture с `state.reset_setup()` перед каждым тестом.

### 4.3. [СРЕДНЕ] Нет тестов для probe-meta async
**Проблема:** Асинхронный probe-meta — ключевая функция, но не тестируется.
**Исправление:** Мокать yt-dlp процесс, проверить цикл job_id → polling → done.

### 4.4. [НИЗКОЕ] Нет тестов для JS
**Проблема:** download.html — 1166 строк JS без единого теста.
**Исправление:** Добавить Jest + jsdom тесты для ключевых функций (renderResButtons, probe polling).

## 5. ПРОБЛЕМЫ UX/ДИЗАЙНА

### 5.1. [КРИТИЧНО] Прогресс-бар скачивания — фейковый
**Где:** `download.html:991-994`
**Проблема:** `bar.style.width = (cur + Math.random() * 6) + '%'` — случайное число! Прогресс-бар не отражает реальный прогресс.
**Исправление:** Парсить процент из yt-dlp output и использовать его.

### 5.2. [СРЕДНЕ] Нет отмены скачивания
**Проблема:** Нельзя остановить скачивание. Только закрыть приложение (и получить zombie process).
**Исправление:** Добавить кнопку «Отмена» + `POST /cancel` endpoint.

### 5.3. [СРЕДНЕ] Нет очереди загрузок
**Проблема:** Одновременно можно скачать только одно видео. При клике на второе — первое прерывается (или нет, зависит от реализации).
**Исправление:** Очередь с возможностью отмены.

### 5.4. [СРЕДНЕ] Нет выбора папки сохранения
**Проблема:** Всегда `~/Downloads`. Нельзя выбрать другую папку.
**Исправление:** Добавить `<input type="file" webkitdirectory>` или `dialog.showDirectoryPicker()`.

### 5.5. [НИЗКОЕ] Длинные URL не обрезаются в поле ввода
**Проблема:** URL длиной 200+ символов ломают layout.
**Исправление:** CSS `text-overflow: ellipsis` для input.

## 6. ПРОБЛЕМЫ СБОКИ И DEPLOY

### 6.1. [КРИТИЧНО] PyInstaller spec ссылается на монолитный server.py
**Где:** `video-downloader-win.spec:14` — `['app.py', 'server.py']`
**Проблема:** При рефакторинге на подпакет spec-файл нужно обновить.
**Исправление:** После рефакторинга — `['app.py', 'server/__init__.py']`.

### 6.2. [СРЕДНЕ] Нет .app bundle для macOS в CI
**Проблема:** CI собирает `Instrumentarium-macos.tar.gz`, но spec для .app не проверяется.
**Исправление:** Добавить проверку `.app` bundle в CI.

### 6.3. [СРЕДНЕ] Нет версионирования в spec-файле
**Проблема:** `name='Instrumentarium'` без версии. При обновлении — перезапись файла.
**Исправление:** Добавить `version='1.0.0'` в spec.

### 6.4. [НИЗКОЕ] Нет code signing для Windows
**Проблема:** SmartScreen будет показывать предупреждение для unsigned .exe.
**Исправление:** `codesign_identity` + EV cert (платно).
